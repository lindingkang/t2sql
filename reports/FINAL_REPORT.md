# Text2SQL Agent 项目总结

> 这是我从零搭起来、完整跑通的一个 Text2SQL 研究项目（Spider benchmark，dev 1034 条 / train 8659 条 / 166 个 sqlite 库）。主线不是"刷榜"，而是**把一套 agent 系统从能跑做到能安全跑、能可复现地评测、能诚实归因**，并在 0.79 → 0.82 的 EA 天花板前，把三条对齐范式（DPO / RFT / GRPO）的失败根因真正挖到了底。
>
> 下面的数字全部可复现，结论全部写进了 `learning_notes.md`（唯一事实源）。负面结果我没有藏——它们恰恰是这个项目最有方法论价值的部分。

---

## 0. 一句话定位

我做了一个 **Text2SQL / 执行反馈 Agent**，走完了 **baseline → prompt 工程 → agent 加固 → SFT → 对齐（DPO / RFT / GRPO）→ 自纠错蒸馏** 的完整链路。最终把"外部 122B 大模型的 agent 管线"蒸馏进"本地 7B 单次前向"（0.7959 vs 0.7834），并用**有根因的负结果**证明了当前 0.8104 是训练分布的局部最优、三范式都推不动的那一两个点。

## 1. 核心指标演进（一眼看全项目）

| 阶段 | 方案 | EA_strict | 关键点 |
|---|---|---|---|
| M0 | 外部 qwen3.5-122b，naive prompt | 0.799 | 起点 |

| M1.5 | 自洽性投票（n=5，5×调用） | 0.796 | **负收益**（多样性不足） |

| M4.5 | SFT + 投票杂交 | 0.8211 | 14.3× 调用，执行兜底 |
| M5 | 确定性 exec 修复（无训练） | **0.8104** | +15 strict 白捡，ER 0.9836 |
| M5 | DPO（薄/厚/强配方） | 0.8104~0.8114 | **零梯度，训练 no-op** |

## 2. 项目背景与目标

**要解决的问题**：自然语言 → SQL（Text2SQL），难点在语义理解（不是语法）、跨表 JOIN、值大小写/格式的"数据描述缺口"。

**我给自己定的规矩**（也是这个项目区别于"刷榜 demo"的地方）：
1. **dev/train 严格隔离**：dev 是唯一评测集，只测不训；所有训练数据（含 DPO/RFT 偏好对）只从 train 构造。
2. **执行准确率当主指标**，且每个数字都有分子/分母（如 `823/1034`）。
3. **生产环境没有 gold**：agent 能用的反馈只有"执行报错 / 结果语义检查 / 自洽性投票"三种，评测用 gold 是另一回事。
4. **单一数字不可信**：千帆 temperature=0 都非确定（±0.7pp），对比实验要么多跑取 mean±std、要么 >2σ 才算显著、要么换本地 greedy 求值。

## 3. 技术主线（分里程碑）

### 3.1 M0–M2：评测基建 + 失败归因 + prompt 触顶

- 搭了执行评测链：`schema.py`（tables.json → DDL）、`run_baseline.py`（只读连接 + 超时 + 行上限 + Latin-1 编码兜底）、`extract_sql`（多行 / markdown fence）。
- **对 207 条失败样本做了逐条 LLM 归因**，得到 7 类错误分布：`semantic_misunderstanding` 33.3% 是最大头、`data_description_gap` 21.7%、`join_error` 17.4%……据此设计了两版 prompt（v1 泛化规则 / v2 精准规则），各跑多次对照。
- **结论**：prompt 工程已触顶（0.799→0.805→0.798，噪声内无显著变化）。模型不是"缺规则"，是"没读懂题"。

> 设计判断：**"我先做了精准归因再动手，而不是拍脑袋改 prompt。归因告诉我真正的瓶颈是语义理解，规则救不了，这直接决定了后面转向微调而不是继续堆 prompt。"**

### 3.2 M1.5 / M3：Agent 骨架 —— 反馈闭环 + 加固

- M1.5 自洽性投票（n=5 采样 → 结果集聚类 → 多数决）实测**负收益**（0.796，5× 调用）。根因：temperature=0.7 对 122B 大模型多样性不足，且**系统性误解无法被投票纠正**（错误 SQL 之间也高度一致）。
- M3 把 agent 从"评测脚本"升级成"工程形态"：
  - **安全层**：SQL AST 白名单，fail-closed，只允许只读单查询（自检 28/28）。
  - **六类降级**：按错误类型差异化重试预算（超时 ⇒ JOIN 理解错，重试价值低）。
  - **空结果二次确认**：带 AST **结构锁**——只允许改值匹配方式，不允许动表/列/JOIN，防止把"正确的空答案"改坏。
  - **成本控制**：自适应投票（3 票早停），平均调用 5.0 → 3.33 次/题。
- **结论**：M3 全开 0.805，第一回**在涨准确率的同时压住成本**。

> 设计判断：**"我把 agent 做到了不能打穿数据库、不会失控烧钱。执行侧安全层 fail-closed，成本侧多数决早停，这是把研究脚本变成可部署系统的关键一步。"**

### 3.3 M4：SFT + 同模型公平对比 —— 项目最重要的一次换挡

- 关键修正：早期数字来自外部 122B，SFT 后是本地 7B，**不能直接比**。于是用同一 7B base 复跑 M0/M1.5/M3，统一分母 1034：

  | 方案（本地 7B） | ER | EA_strict |
  |---|---|---|
  | M0 local base | 0.9246 | 0.7340 |
  | M1.5 投票 | 0.9894 | 0.7708 |
  | M3 agent | 0.9894 | 0.7834 |
  | M4 SFT（单次前向） | 0.9594 | **0.7959** |

- **核心叙事**：本地 7B **单次前向**（0.7959）就超过了本地 agent 管线（5.16 次调用 + 重试 + 投票 = 0.7834）。**本质是"把 agent 的能力蒸馏进单次生成"**——这是比"涨了 1.26 个点"更有说服力的部署故事。
- 训练：QLoRA（4bit NF4 + LoRA r=16），数据只来自 train，做完**泄漏审计**（真泄漏 0 条）。

### 3.4 M4.5 / M5：执行层兜底 —— 确定性修复白捡 +15 strict

- M4.5 投票杂交把 ER 拉到 1.0、strict 到 0.8211，但代价 14.3× 调用；收益分解发现 **61% 是"执行兜底"而非"语义纠正"**。
- M5 Step1 **确定性 exec 修复**（无训练、无 LLM）：只改三类"有把握"的机械错误（双引号→单引号、表/列名大小写/单复数笔误、跨表列重指派），sqlglot AST 改写 + difflib 模糊，"宁可不改也不改错"。
  - 结果：+25 ER / **+15 EA_strict**，基线从 0.7959 抬到 **0.8104**（ER 0.9836），零训练成本。
- **这是整个项目最干净的一次"白捡"。**

> 设计判断：**"我要先确定性地、零成本地抠掉能抠的部分，再让数据驱动的训练去啃剩下的硬骨头。这是研究员该有的收益优先级——先确定性、再监督、最后 RL。"**

### 3.5 M6：两块叙事空白 —— 自纠错蒸馏（正信号）+ GRPO（负结果）

**第一块：repair-aware SFT（training-time 自纠错）。**
把 agent 的 `act→observe→correct` **单跳**从规则层（`degrade.py` + `exec_repair.py`）蒸馏进**权重层**：训练模型在"自己生成的错 SQL + sqlite 报错"下直接吐出修正 SQL。
- 数据：27 条真实模型 exec 错误（有机核心）+ 3000 条合成破坏（train gold 反注入，三类各 1000）+ 3027 条 50% 反遗忘锚点 = 6054 行；从 `sft_cons_v1` 续训（rank16 / lr1e-4 / 1ep）。
- 评测（dev 的 46 条执行失败，oracle 可修 28 / 不可修 18）：自纠错**内部化率 71% → 82%**，且**总体 strict 17/46 反超规则 oracle 16/46**——模型学到的纠错泛化到规则"不可修"的 18 条之外，这正是"蒸馏进权重"比"规则层"值钱的那一点。

**端到端验证（把 bench demo 升级成真实 agent 能力）：**
把 `repair_r1` 接回 agent 的重试路径，在 dev 的 46 条执行失败样本上对比三种纠正器：

| 纠正器 | exec 恢复 | strict |
|---|---|---|
| single-pass (turn-0) | 0/46 | 0/46 |
| 规则 oracle (`exec_repair`) | 28/46 | 16/46 |
| 模型自纠错（`repair_r1`） | **27/46** | **17/46** |
| agent 现状（规则 hint + 外部 122B 重写） | **46/46** | **32/46** |

结论（诚实、不吹）：
1. `repair_r1` 在真实重试循环里 ≈ 规则 oracle（27 vs 28 exec），strict 反超（17 vs 16）——**"权重 ≈ 规则"在 agent 里成立**。
2. 但 agent 现状（规则提示 + 外部大模型）能 100% 恢复。7B 蒸馏只捕获其 ~59%。差距来源：**(a) 模型容量**（7B vs 122B）、**(b) 提示信息差**（repair_r1 训练用裸报错，agent 现状喂的是含"相似列+可用列"的富提示）。→ 这两点直接指向 §5 的 future work。
3. 定位：`repair_r1` 是"**本地免费的规则层等价物**"，已把"看到报错→改"内化成 7B 权重，零 API 成本/延迟。

> 设计判断：**"我把 inference-time 的纠错能力蒸馏进了一个本地 7B 权重。它不是要替代更大的模型，而是证明'agent 的一跳闭环可以被压缩进权重',并在真实 retry 路径上验证了它达到规则层的水平。"**

## 4. 这一路最大的收获：三范式合流的负结果

这是我认为最有价值的部分——**三条对齐范式各自失败的根因，最终收敛到同一个结论**。

| 范式 | 尝试 | 现象 | 根因 |
|---|---|---|---|
| DPO（偏好式） | 2047 偏好对，β/lr/epochs 全扫 | EA 与基线逐字节一致 | 加载顺序 bug 冻死 LoRA（0 训练参数）；修好后仍只学 token 措辞，不迁移语义 |
| RFT/STaR（重放式） | 589 STaR chosen + 123 hardgold | 最佳 +0.10pp ≈ 无；干净对照 **−0.19pp** | 样本全是模型自己 359 道 train 错误里 pass 出来的，round-1 已训过，边际信息量≈0 |
| GRPO（在线式） | 200 题 × 100 步 × G8，稠密四档 reward | loss→1e-9、grad_norm→1e-6、entropy 0.10→0.015 | 起点模型在 train 上 reward mean→1.0，**on-distribution 饱和 + 熵塌缩 → 零梯度** |

**一句话合流**：
> DPO 零梯度、RFT 边际信息≈0、GRPO on-distribution 饱和——三条路的根是**同一个**：0.8104 的 SFT 模型已经是其训练分布的局部最优，任何同分布微调（偏好式/生成式/在线式）都推不动那一两个 pp。

几个"科学家式诚实"的具体证据（我可以逐条展开）：
- DPO 训练无效果时，我**逐张量比对**了 adapter 权重（392/392 与 SFT bit 完全相同、max 相对偏移 0.0），确认是冻结 bug 而非"数据太少"。
- RFT 我先做了 **2×2 消融**（数据 × epochs），才推翻自己上一版"+0.87pp 有效"的错误结论（那其实是"数据抵消过拟合"，不是"叠出新能力"）。
- GRPO 在动手前就**预言了失败机制**（71% 单签名 → 组内零方差 → advantage 崩），并用稠密四档 reward 作对策；sanity 精确复现了预言（≈75% 批次零方差），同时证明"稠密 reward 在难题上确实保住了方差"——只是熵塌缩让梯度还是死了。

## 5. Future Work（真正的杠杆在哪）

三条范式共同失效已经告诉我们：**继续往同分布数据砸训练，边际收益是零**。真正的杠杆只剩四个方向，按我认为的优先级排：

1. **数据多样性**：引入分布外数据填补 train/dev 的泛化缺口——Spider-DK（领域知识）、Spider-Syn（同义改写）、BIRD（更大规模、更真实的跨领域 Text2SQL）。当前模型的 semantic_misunderstanding（33% 失败）本质是"没见过这种问法/领域"，补分布外数据是治本。
2. **模型容量**：7B → 14B / 32B，或直接换更强的 code 基座。端到端实验已经量化了这个缺口——同样的报错起点，外部 122B + 规则提示能 46/46 恢复，本地 7B 只恢复 27/46（59%）。
3. **真实多轮 agentic RL**：用 M3 存下来的**完整重试轨迹**做**轨迹级 GRPO**（当前 GRPO 只做了单步 RL，没有把"重试"这个多轮过程本身作为优化对象）。这才是"agentic RL"的完整形态。
4. **稠密奖励 + 过程监督**：当前只用结果奖励（可执行/行数/loose/strict）。可以引入 **SQL 结构相似度**做过程奖励（JOIN 路径对不对、聚合层级对不对），给 RL 一个"部分正确"的梯度信号，缓解零方差/稀疏奖励。

> 核心判断再强调一句：**第一步该做的不是再训，而是先换数据分布**——因为 RFT 的 −0.19pp 已经从反面证实了"同分布数据再多也白搭"。

## 6. 可迁移的方法论

1. **全栈 ML 工程**：从数据造集（泄漏审计 / 反遗忘锚点 / 反注入合成）到训练（QLoRA / 续训 / LoRA 合并）到评测（同模型公平基准 / 自检框架）到部署叙事（蒸馏进单次生成）。
2. **Agent 系统设计**：安全层（fail-closed AST 白名单）、反馈闭环（执行报错 → 分类 → 差异化重试）、成本控制（自适应早停 + 缓存 + token 预算）。
3. **严谨的评测方法论**：精准归因（逐条 LLM diagnose）、均值±std / >2σ、同模型基准、确定性求值 vs API 非确定的取舍。
4. **有根因的负结果**：不把"失败"藏起来，而是定位到"冻死 LoRA 的加载顺序"或"熵塌缩导致 advantage 崩"这一层。这在业界是稀缺品质。
5. **诚实给收益定性**：每步明确"这是执行兜底还是语义纠正""这是 +3 条的 demo 还是 EA 级突破"，不把 46 条的增量吹成刷榜。

- **蒸馏线**（部署）："我先把外部 122B 的 agent 管线（投票+重试+空结果确认）蒸馏成本地 7B 单次前向（0.7834 → 0.7959），再把它的单跳自纠错也从规则层蒸馏进权重（71%→82%）。"
- **负结果线**（科学素养）："我完整试了 DPO / RFT / GRPO 三种对齐范式，各自失败，但根因收敛到同一个结论——起点模型已在其训练分布饱和。我用逐张量比对、2×2 消融、预言-复现三种手段把根因挖到了底。"
- **工程线**（落地）："我把 agent 做成了 fail-closed 安全层 + 确定性 exec 修复 + 自适应成本控制，每一步都有独立 self-test 和可复现的数字。"
